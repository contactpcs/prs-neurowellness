About This Review
This document is a production readiness assessment of the NeuroWellness Patient Rating System (PRS) frontend, a healthcare platform built with Next.js 14 App Router, Redux Toolkit, and TypeScript. The review covers architecture, security, performance, scalability, and code quality from the perspective of a Principal Frontend Architect preparing the codebase for production deployment.
⚠ HIPAA Notice
This is a healthcare application handling Protected Health Information (PHI). Several findings in this review are not merely engineering best practices — they are potential HIPAA compliance violations. Section 6 (Security) must be treated as highest priority before any production deployment.

Project Architecture 7 / 10

✓ Strengths

  • Route groups (auth) / (roles) cleanly separate public and protected shells — correct Next.js 14 pattern
  • lib/api/services/, lib/hooks/, types/, store/slices/ — genuine vertical separation of concerns
  • Barrel exports (index.ts) everywhere — clean, consistent imports
  • lib/constants/index.ts — single source of truth for roles, routes, storage keys
  • CVA + Tailwind for UI system — industry-standard approach

✗ Issues

  • No .env.example — impossible to bootstrap without asking someone
  • components/test/ mentioned but orphaned/empty
  • any leaks: rawUser: any in normalizeUser, as any on roles — TypeScript strict mode partially defeated
  • No global error boundary in app shell
  • src/data/conditionMap.json — static JSON committed to src/; should be in public/ or a proper seeded query

Section 02
System Design 6 / 10

Data Flow Architecture

User action → Custom Hook → Redux Thunk → Service → Axios → API Backend ↓ Component re-render ← Redux State ← Fulfilled Thunk ←──┘ Route Entry: Page (container) → Feature Components (hooks) → UI Components (pure presentational)

Component Hierarchy

RootLayout (StoreProvider + AuthProvider) └─ (roles)/layout.tsx [auth guard + SidebarProvider] ├─ Sidebar (navigation, role-based links) └─ main └─ Page.tsx [data fetching via hooks] └─ Feature Components [useDoctor / usePatient / etc] └─ UI Components [Button / Card / Input — pure]

Critical Gaps

IssueSeverityImpact at Scale
No refresh token implementationCriticalUsers force-logged-out mid-assessment after token expiry
window.location.href on 401HighBypasses Next.js router; full page reload; breaks back-button; can cause redirect loops
No pagination in list hooksHighDoctors with 100+ patients fetch entire list on mount; unbounded API response
No WebSocket / real-timeMediumNotifications require manual refresh; not viable at 100K+ users
Authorization only at layout levelMediumNo per-component or per-action RBAC; role check is coarse-grained
No optimistic updatesLowMutations feel slow; user waits for round-trip before UI updates

Can This Scale to 100K+ Users?

Frontend is CDN-deployable and stateless — yes, it can scale horizontally. The perceived scaling issues are API design gaps (no pagination) and UX gaps (no real-time), not fundamental architecture flaws. The backend carries the actual load.

What fails first: Token expiry causing mass logouts during long sessions, then unbounded patient list fetches causing slow load times and memory bloat for power users.

Section 04
Performance Audit 5.5 / 10

Issues Ranked by Impact

P0 — No Code Splitting by Role
Every user role ships every route's code in one bundle. A patient downloads doctor, admin, CA, and receptionist bundles they will never use. Estimated overhead: 30–40% excess JavaScript. 
// Fix: dynamic imports per page
const DoctorDashboard = dynamic(() => import('./DoctorDashboard'), { ssr: false });
const AssessmentUI = dynamic(() => import('@/components/assessment/AssessmentUI'));
P0 — No Memoized Selectors
All catalog selectors return unstable references. Any Redux dispatch causes re-render in every component using selectScales, selectConditions, etc., even if those values didn't change. 
// CURRENT — new reference on every state change
export const selectScales = (s: RootState) => s.catalog.scales;

// FIX — stable reference via createSelector
import { createSelector } from '@reduxjs/toolkit';
export const selectScales = createSelector(
  (s: RootState) => s.catalog.scales,
  (scales) => scales
);
P1 — window.location.href on 401 Causes Full Page Reload
Forces complete React tree unmount + remount instead of client-side navigation. All in-memory state lost. Visible as a blank flash to the user. 
// CURRENT — in client.ts:27
window.location.href = '/login';

// FIX — use Next.js router (requires passing router ref or using a singleton)
import { AppRouterInstance } from 'next/dist/shared/lib/app-router-context.shared-runtime';
// OR: use a router singleton pattern, or dispatch an event to the auth slice
P1 — No Pagination on List Endpoints
Patient lists, score history, notification feeds, and session lists load all records on mount. At 100+ records per user, this becomes a UX and memory problem. Add skip/limit parameters to all list service methods immediately.

Scalability Assessment 6 / 10
ScaleFrontend VerdictWhat Breaks FirstPrevention
10K users ✓ Works as-is Nothing frontend-critical —

What Fails First at 100K Users

  1. Pagination gap — A doctor with 200 patients loads all 200 on every dashboard mount. At 100K users with 20 doctors each having 200 patients, you have 4M patient records being fetched in full lists.
  2. Token expiry — Access tokens expire (typically 30–60 mins) with no refresh logic. Patients filling a 60-question assessment get force-logged-out mid-session, losing all answers. At scale, this creates support ticket floods.
  3. Notification polling — Without WebSocket, every notification check is a new HTTP request. At 100K concurrent users polling every N minutes, this is millions of requests/hour for a simple read operation.

Assessment Data Loss — Critical UX Issue at Any Scale

The questionnaire state lives only in Redux memory. A network drop, browser refresh, or accidental tab close during a 30-minute multi-scale assessment destroys all answers. The state shape in questionnaireSlice is already perfect for persistence — it just needs to be written to localStorage on every setAnswer.

// questionnaireSlice.ts — add localStorage persistence
setAnswer: (state, action) => {
  const { scaleId, questionIndex, value } = action.payload;
  if (!state.responses[scaleId]) state.responses[scaleId] = {};
  state.responses[scaleId][String(questionIndex)] = value;

  // Persist draft to localStorage to prevent data loss on network drop
  if (state.sessionId) {
    localStorage.setItem(
      `prs_draft_${state.sessionId}`,
      JSON.stringify(state.responses)
    );
  }
},
